# 设计模式使用规范

> 基于 GoF 23 种设计模式，结合 SOLID 原则和阿里巴巴设计规约，定义适用于本项目的模式选用规则。
> 约束力分为 **【强制】**、**【推荐】**、**【参考】** 三级。

## 一、设计原则（SOLID）

| 原则 | 全称 | 核心要义 |
|---|---|---|
| **S**RP | 单一职责原则 (Single Responsibility) | 一个类只负责一个功能领域中的相应职责 |
| **O**CP | 开闭原则 (Open-Closed) | 对扩展开放，对修改关闭 |
| **L**SP | 里氏替换原则 (Liskov Substitution) | 子类对象必须能够替换掉所有父类对象 |
| **I**SP | 接口隔离原则 (Interface Segregation) | 客户端不应该依赖它不需要的接口 |
| **D**IP | 依赖倒置原则 (Dependency Inversion) | 依赖于抽象，不依赖于具体实现 |

### 【强制】补充原则

| 原则 | 全称 | 核心要义 |
|---|---|---|
| **DRY** | Don't Repeat Yourself | 系统中不出现重复代码，共性逻辑必须抽取 |
| **KISS** | Keep It Simple, Stupid | 保持简单，避免过度设计 |
| **YAGNI** | You Aren't Gonna Need It | 不要提前实现当前不需要的功能 |
| **LoD** | 迪米特法则 (Law of Demeter) | 一个对象应该对其他对象保持最少的了解 |

## 二、通用使用规则

### 【强制】

1. 使用设计模式时，类名/接口名需体现模式名称。正例：`OrderFactory`、`LoginProxy`、`LogisticsStrategy`。
2. 禁止为了使用模式而使用模式。设计模式的引入必须解决实际问题，不得增加不必要的抽象层次。
3. 优先使用组合/聚合，而不是继承。只有当子类确实是父类的特殊类型时才使用继承。
4. 面向接口编程，依赖抽象而非具体实现。通过依赖注入解耦模块间关系。
5. 对扩展开放，对修改关闭。新增功能时优先通过扩展（新类、新接口、新策略）来实现，而非修改已有代码。
6. 模式实现中不得出现重复的样板代码，公共逻辑应抽取到父类或工具方法中。

### 【推荐】

1. 设计模式的选择应基于场景需求，而非个人偏好。
2. 模式的引入应在系统设计阶段确定，不应在编码阶段临时引入。
3. 一个模式只解决一个问题，避免将多个模式强行揉合在一起。
4. 使用模式后必须编写单元测试，验证模式行为的正确性和可扩展性。

## 三、创建型模式（5 种）

> 关注对象的创建机制，提供创建对象的灵活性并将创建逻辑与使用逻辑分离。

### 3.1 工厂方法模式 (Factory Method)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要根据不同条件创建不同子类对象；创建逻辑复杂或需要隐藏创建细节 |
| **本项目参考** | 平台策略创建：`LogisticsExceptionScannerRegistry.get(platform)` 根据平台标识获取对应的扫描策略 |
| **禁止场景** | 对象创建逻辑简单且只有一个实现类时 |

### 3.2 抽象工厂模式 (Abstract Factory)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要创建一系列相关或相互依赖的对象；产品族维度多变 |
| **禁止场景** | 只有一种产品族，或产品族维度不会扩展 |

### 3.3 单例模式 (Singleton)

| 维度 | 说明 |
|---|---|
| **适用场景** | 全局唯一的共享资源管理（配置、缓存、连接池等） |
| **实现方式** | 推荐使用枚举实现或双重检查锁（DCL）；Spring Bean 默认单例，优先使用 Spring 容器管理 |
| **禁止场景** | 持有可变状态且需要在测试中替换的场景；使用 Spring 的类不需要手动实现单例 |

### 3.4 建造者模式 (Builder)

| 维度 | 说明 |
|---|---|
| **适用场景** | 复杂对象的构建过程需要分步骤进行；同一构建过程可创建不同表示；参数超过 4 个的对象构造 |
| **本项目参考** | 使用 Lombok `@Builder` 注解或手写 Builder 内部类 |
| **禁止场景** | 简单对象（少于 4 个参数）直接使用构造方法或 setter |

### 3.5 原型模式 (Prototype)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要创建与现有对象相同的副本，且创建成本高于拷贝成本 |
| **禁止场景** | 对象结构简单、创建成本低；需要注意深拷贝和浅拷贝的问题 |

## 四、结构型模式（7 种）

> 关注类和对象的组合，处理不同对象间的关系，构建更灵活的结构。

### 4.1 适配器模式 (Adapter)

| 维度 | 说明 |
|---|---|
| **适用场景** | 已有类的接口与目标接口不匹配；需要复用已有类但无法修改其接口 |
| **禁止场景** | 在新系统中可以提前设计统一接口时，不应事后用适配器弥补设计缺陷 |

### 4.2 装饰器模式 (Decorator)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要动态地给对象添加职责；功能可叠加组合 |
| **禁止场景** | 功能简单且不会动态组合；过度嵌套会导致层级过深难以维护 |

### 4.3 代理模式 (Proxy)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要控制对对象的访问（权限、延迟加载、远程调用、日志等） |
| **本项目参考** | Spring AOP 已提供动态代理能力，优先使用 `@Aspect` 而非手写代理类 |
| **禁止场景** | 不需要额外控制逻辑时直接调用目标对象 |

### 4.4 外观模式 (Facade)

| 维度 | 说明 |
|---|---|
| **适用场景** | 为复杂子系统提供统一入口；降低子系统与客户端的耦合度 |
| **本项目参考** | Kafka 事件推送入口 `KafkaUtils.push()` 统一封装底层 Producer 细节 |
| **禁止场景** | 子系统本身已经足够简单 |

### 4.5 桥接模式 (Bridge)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要在两个独立变化的维度上扩展（如平台 × 核验类型） |
| **禁止场景** | 只有一个变化维度时使用继承即可 |

### 4.6 组合模式 (Composite)

| 维度 | 说明 |
|---|---|
| **适用场景** | 树形结构的数据处理；需要统一对待叶子节点和组合节点 |
| **禁止场景** | 数据结构本身不是树形 |

### 4.7 享元模式 (Flyweight)

| 维度 | 说明 |
|---|---|
| **适用场景** | 大量细粒度对象复用（如缓存池、连接池） |
| **禁止场景** | 对象数量少或对象状态不可共享 |

## 五、行为型模式（11 种）

> 关注对象间的通信和职责分配，定义对象间交互的算法。

### 5.1 策略模式 (Strategy)

| 维度 | 说明 |
|---|---|
| **适用场景** | 同一行为在不同条件下有不同的实现；需要在运行时切换算法 |
| **本项目参考** | `LogisticsExceptionScanner` / `LogisticsRechecker` 接口，不同平台不同实现，通过 Registry 动态查找 |
| **禁止场景** | 只有单一实现且不会扩展时 |

### 5.2 模板方法模式 (Template Method)

| 维度 | 说明 |
|---|---|
| **适用场景** | 多个类有相同的方法骨架但具体步骤不同；固定算法骨架，子类实现可变步骤 |
| **本项目参考** | `AbstractPlatformClient` 定义平台客户端的通用流程，子类实现平台差异部分 |
| **禁止场景** | 算法步骤不需要复用，或子类差异过大导致模板方法臃肿 |

### 5.3 观察者模式 (Observer)

| 维度 | 说明 |
|---|---|
| **适用场景** | 一个对象的状态变化需要通知多个依赖对象；事件驱动的解耦 |
| **本项目参考** | Kafka 消息发布/订阅模式，Producer 发送事件，Consumer 监听处理 |
| **禁止场景** | 通知对象数量固定且少，直接调用更简单 |

### 5.4 责任链模式 (Chain of Responsibility)

| 维度 | 说明 |
|---|---|
| **适用场景** | 多个处理器按顺序处理同一请求，且每个处理器可决定是否传递 |
| **禁止场景** | 处理逻辑固定且只有一个处理器；链路过长导致难以追踪 |

### 5.5 命令模式 (Command)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要将请求封装为对象；支持撤销/重做、队列、日志等 |
| **本项目参考** | `LogisticsSelfVerifyCommand` 封装核验调度指令，通过 Kafka 传递并由 Consumer 执行 |
| **禁止场景** | 请求逻辑简单，直接方法调用即可 |

### 5.6 状态模式 (State)

| 维度 | 说明 |
|---|---|
| **适用场景** | 对象的行为随内部状态变化而变化；状态转换逻辑复杂 |
| **本项目参考** | `OrderLogisticsExceptionStatus` 枚举定义异常状态流转 |
| **禁止场景** | 状态少且行为差异小 |

### 5.7 迭代器模式 (Iterator)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要统一遍历不同聚合结构 |
| **禁止场景** | Java 集合框架已内置迭代器支持，通常不需要自行实现 |

### 5.8 中介者模式 (Mediator)

| 维度 | 说明 |
|---|---|
| **适用场景** | 多个对象间存在复杂的网状交互，需要通过中介者解耦 |
| **禁止场景** | 对象间交互简单 |

### 5.9 备忘录模式 (Memento)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要保存和恢复对象的状态 |
| **禁止场景** | 状态数据量大且不需要回溯 |

### 5.10 访问者模式 (Visitor)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要对一组结构固定的对象执行多种不同的操作，且操作经常变化 |
| **禁止场景** | 对象结构不稳定，频繁新增类型 |

### 5.11 解释器模式 (Interpreter)

| 维度 | 说明 |
|---|---|
| **适用场景** | 需要解析和执行某种语言或表达式 |
| **禁止场景** | 语法规则简单，直接硬编码即可；本项目中极少使用 |

## 六、模式选型决策表

| 需求场景 | 推荐模式 | 禁止使用 |
|---|---|---|
| 根据条件创建不同对象 | 工厂方法 / 抽象工厂 | 直接 `if-else` 硬编码 |
| 全局唯一实例 | Spring 单例 / 枚举单例 | 手写 DCL（Spring 项目中） |
| 复杂对象分步构建 | Builder | 过多参数的构造方法 |
| 动态添加功能 | 装饰器 / 代理 | 继承堆叠 |
| 统一子系统入口 | Facade | 客户端直接依赖所有子系统 |
| 运行时切换算法 | 策略模式 | 继承 + 重写方法 |
| 固定流程+可变步骤 | 模板方法 | 复制粘贴流程代码 |
| 事件通知 | 观察者 / Kafka | 直接调用多个对象 |
| 状态流转 | 状态模式 | 大量 `if-else` 判断状态 |
| 请求封装与排队 | 命令模式 | 直接方法调用 |

## 七、反模式清单

### 【强制】禁止以下做法

1. **God Class（上帝类）**：一个类承担过多职责，违反 SRP。
2. **Shotgun Surgery（霰弹式修改）**：一个变更需要修改多个分散的类，说明职责划分不合理。
3. **Feature Envy（依恋情结）**：一个方法过度关注其他类的数据，说明行为放错了位置。
4. **Dead Code（死代码）**：不再被调用的代码必须删除，不保留注释掉的代码。
5. **Boat Anchor（船锚）**：保留不再使用的设计模式代码"以备将来"。
6. **Poltergeist（幽灵类）**：仅负责传递数据而不包含任何业务逻辑的临时类。
7. **Golden Hammer（金锤子）**：对任何问题都用同一个设计模式解决。
8. **Spaghetti Code（面条代码）**：无清晰结构的流程式代码，无面向对象设计。
9. **过度设计（Over-engineering）**：为不存在的未来需求提前设计复杂架构，违反 YAGNI。
10. **魔法值**：未定义常量直接出现在代码中。
