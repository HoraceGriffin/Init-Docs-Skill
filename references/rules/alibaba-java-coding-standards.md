# 阿里巴巴 Java 开发规范

> 基于《阿里巴巴 Java 开发手册（黄山版）》整理，约束力分为 **【强制】**、**【推荐】**、**【参考】** 三级。

## 一、编程规约

### 1.1 命名风格

#### 【强制】

1. 代码中的命名均不能以下划线或美元符号开始，也不能以下划线或美元符号结束。
2. 严禁使用拼音与英文混合的方式命名，禁止使用不规范的缩写。
3. 禁止使用歧视性词语：
   - `blackList` → `blockList`
   - `whiteList` → `allowList`
   - `slave` → `replica`
   - `master` → `main` / `default`
4. 类名使用 `UpperCamelCase`（大驼峰）命名法，但 BO、PO、VO、DTO 等领域模型例外。
5. 抽象类命名使用 `Abstract` 或 `Base` 开头；异常类命名使用 `Exception` 结尾；测试类命名使用「被测试类名 + Test」。
6. 方法名、参数名、成员变量、局部变量均使用 `lowerCamelCase`（小驼峰）命名法。
7. 常量命名全部大写，单词间用下划线隔开，力求语义表达完整，不要嫌名字长。
8. 包名统一使用小写，点分隔符之间仅有一个自然语义的英语单词。包名统一使用单数形式。
9. 枚举类名建议带上 `Enum` 后缀，枚举成员名称需要全大写，单词间用下划线隔开。

#### 【推荐】

1. 如果模块、接口、类、方法使用了设计模式，在命名时需体现出具体模式。正例：`OrderFactory`、`LoginProxy`。
2. 接口和实现类命名：
   - 对于 Service 和 DAO 类，暴露出来的服务一定是接口，内部的实现类用 `Impl` 后缀与接口区别。
   - 如果是形容能力的接口名称，取对应的形容词为接口名（通常是 `able` 为词根）。正例：`AbstractTranslator` 实现 `Translatable` 接口。

### 1.2 常量定义

#### 【强制】

1. 不允许任何魔法值（即未经预先定义的常量）直接出现在代码中。
2. 在 long 或者 Long 赋值时，数值后使用大写字母 `L`，不得使用小写字母 `l`，容易跟数字 `1` 混淆。

#### 【推荐】

1. 不要使用一个常量类维护所有常量，要按常量功能进行归类，分开维护。
2. 常量的复用层次：
   - 跨应用共享常量：放置在二方库中
   - 应用内共享常量：放置在一方库中，通常是子模块的 `constant` 目录下
   - 子工程内共享常量：在当前子工程的 `constant` 目录下
   - 包内共享常量：在当前包下单独的 `constant` 目录下
   - 类内共享常量：直接在类内部 `private static final` 定义

### 1.3 代码格式

#### 【强制】

1. 单个方法的总行数（不包括注释）不超过 **80** 行。
2. 不同的逻辑、语义、业务的代码之间可插入一个空行分隔开来以提升可读性，但任何情形下都没必要插入多个空行进行分隔。

### 1.4 OOP 规约

#### 【强制】

1. 所有的覆写方法必须加 `@Override` 注解。
2. 不能使用过时的类或方法。如果接口过时必须加 `@Deprecated` 注解，并说明采用的新接口或新服务。
3. `Object` 的 `equals` 方法容易抛 NPE，应使用常量或确定有值的对象来调用 `equals`。推荐使用 `java.util.Objects#equals`。
4. 所有整型包装类对象之间值的比较，全部使用 `equals` 方法比较。
5. 任何货币金额均以最小货币单位的整型来存储。
6. 浮点数之间的等值判断，不能使用 `==`，也不能使用 `equals`，应指定误差范围或使用 `BigDecimal`。
7. `BigDecimal` 使用 `compareTo()` 而非 `equals()` 进行值比较（`equals` 会比较精度）。
8. 定义 DO 类时，属性类型要与数据库字段类型相匹配。
9. POJO 类的属性、RPC 方法的返回值和参数都必须使用包装数据类型。
10. 所有的局部变量使用基本数据类型。
11. 构造方法里禁止加入业务逻辑，初始化逻辑可放在 `init` 方法中。
12. POJO 类属性禁止设定默认值。
13. POJO 类必须写 `toString` 方法。
14. 禁止在 POJO 类中同时存在对应属性 `xxx` 的 `isXxx()` 和 `getXxx()` 方法。

#### 【推荐】

1. 禁止使用 Apache Beanutils 进行属性 copy（性能较差），可用 Spring BeanUtils 或 Cglib BeanCopier，但均是浅拷贝。

### 1.5 日期时间

#### 【强制】

1. 日期格式化时，传入 pattern 中表示年份统一使用小写 `y`，禁止使用大写 `Y`（`Y` 表示 week year，跨年时会产生错误）。
2. `H` 表示 24 小时制，`h` 表示 12 小时制。
3. 推荐使用 `Instant`、`LocalDate`、`LocalTime` 和 `LocalDateTime`，禁止使用 `java.sql.Date`、`java.sql.Time`、`java.sql.Timestamp`。
4. 禁止在程序中硬编码一年为 365 天。
5. `SimpleDateFormat` 是线程不安全的类，禁止定义为 `static` 变量。推荐使用 `DateTimeFormatter` 代替。

### 1.6 集合处理

#### 【强制】

1. 只要重写 `equals`，就必须重写 `hashCode`。
2. 使用 `isEmpty()` 代替 `size() == 0` 判空。
3. 禁止在 `foreach` 循环里进行元素的 `remove`/`add` 操作。`remove` 需使用 `Iterator` 方式；并发操作则要对 `Iterator` 对象加锁。

```java
// 正例
Iterator<String> iterator = list.iterator();
while (iterator.hasNext()) {
    String item = iterator.next();
    if ("1".equals(item)) {
        iterator.remove();
    }
}
// 反例
for (String item : list) {
    if ("1".equals(item)) {
        list.remove(item);
    }
}
```

#### 【推荐】

1. 集合初始化时指定集合初始值大小。
2. 利用 `Set` 对集合去重，避免使用 `List` 的 `contains()` 遍历去重。
3. 使用 entrySet 遍历 Map 类集合，而不是用 keySet 方式遍历。

### 1.7 并发处理

#### 【强制】

1. 创建线程或线程池时必须指定有意义的线程名称。
2. 线程资源必须通过线程池提供，不允许在应用中自行显式创建线程。
3. 线程池禁止用 `Executors` 去创建，必须通过 `ThreadPoolExecutor` 的方式创建（`Executors` 返回的线程池存在 OOM 风险）。
4. 必须回收自定义的 `ThreadLocal` 变量，在线程池场景下尤其重要。使用 `try-finally` 块回收：

```java
objectThreadLocal.set(userInfo);
try {
    // ...
} finally {
    objectThreadLocal.remove();
}
```

5. 加锁的代码块工作量尽可能小：
   - 能用无锁数据结构的就不要用锁
   - 能锁区块的就不要锁整个方法体
   - 能用对象锁的就不要用类锁
6. 阻塞等待获取锁时必须在 `try` 块之外获取锁，在 `finally` 块中释放锁：

```java
Lock lock = new XxxLock();
lock.lock();
try {
    doSomething();
} finally {
    lock.unlock();
}
```

7. 尝试机制获取锁时必须判断是否持有锁：

```java
boolean isLocked = lock.tryLock();
if (isLocked) {
    try {
        doSomething();
    } finally {
        lock.unlock();
    }
}
```

8. 禁止 `HashMap` 在多线程下使用 `put`（resize 时可能导致死链）。

#### 【推荐】

1. 若每次访问冲突概率小于 20% 则用乐观锁，否则用悲观锁。乐观锁的重试次数需大于 3 次。
2. 资金相关的金融敏感信息使用悲观锁策略。
3. 悲观锁遵循「一锁、二判、三更新、四释放」原则。
4. 推荐使用 `ThreadLocalRandom` 代替共享 `Random` 实例。

### 1.8 控制语句

#### 【强制】

1. 在一个 `switch` 块内，都必须包含一个 `default` 语句且放在最后，即使它没有代码。
2. `switch` 括号内的变量类型为 `String` 且此变量为外部参数时，必须先进行 `null` 判断。
3. 在 `if`/`else`/`for`/`while`/`do` 语句中，即使只有一行代码也要使用大括号 `{}`。
4. 不要在条件判断中执行复杂的语句，将复杂逻辑判断结果赋值给一个有意义的布尔变量名。
5. 不要在其它表达式中插入赋值语句。

### 1.9 注释规约

#### 【强制】

1. 类、类属性、类方法的注释必须使用 Javadoc 规范，使用 `/** 内容 */` 格式，不得使用 `// xxx` 方式。
2. 所有的类都必须添加创建者和创建日期。
3. 方法内部单行注释使用 `//`，在被注释语句上方另起一行。方法内部多行注释使用 `/* */`。
4. 所有的枚举类型字段都要有注释，说明每个数据项的用途。
5. 代码与注释要同步更新。

#### 【推荐】

1. 方法注释要包含返回值、参数、异常说明。抽象方法还必须指出该方法做什么事情、实现什么功能、对子类的实现要求。

### 1.10 其他

#### 【强制】

1. 正则表达式需要利用好预编译功能，可以有效加快正则匹配速度。定义为 `static final Pattern`。
2. 任何数据结构的构造或初始化都应指定大小，避免无限增长吃光内存。

## 二、异常日志

### 2.1 错误码

#### 【强制】

1. 错误码为字符串类型，共 5 位，分成两个部分：错误产生来源 + 四位数字编号。
   - 来源：`A` 用户、`B` 当前系统、`C` 第三方服务
   - 编号：从 `0001` 到 `9999`，大类之间步长间距预留 `100`
2. 错误码不能直接输出给用户作为提示信息使用。

### 2.2 异常处理

#### 【强制】

1. 可以通过预检查方式规避的 `RuntimeException` 禁止通过 `catch` 来处理（如 `NullPointerException`、`IndexOutOfBoundsException`）。
2. `catch` 尽可能将异常类型区分，再做对应的异常处理。禁止对大段代码进行 `try-catch`。
3. 禁止捕获异常却什么都不处理。
4. 禁止在 `finally` 块中使用 `return`。
5. `finally` 块必须对资源对象、流对象进行关闭，推荐使用 `try-with-resources` 方式。
6. 禁止直接抛出 `new RuntimeException()`，禁止抛出 `Exception` 或 `Throwable`，应使用有业务含义的自定义异常（如 `DAOException`、`ServiceException`）。
7. 方法的返回值可以为 `null`，但必须添加注释说明什么情况下会返回 `null`。

#### 【推荐】

1. 防止 NPE，推荐使用 `Optional`。注意以下场景的 NPE：
   - 数据库查询结果可能为 null
   - 集合中取出的元素可能为 null
   - 远程调用返回对象必须做空指针判断
   - 级联调用 `obj.getA().getB().getC()` 易产生 NPE
2. 在调用 RPC、二方包或动态生成类的相关方法时，捕捉异常要用 `Throwable` 来拦截。

### 2.3 日志规约

#### 【强制】

1. 不可直接使用日志系统（Log4j、Logback）中的 API，应使用 SLF4J 中的 API（门面模式）。
2. 生产环境禁止使用 `System.out`、`System.err`、`e.printStackTrace()`。
3. 异常信息必须包含两类信息：案发现场信息和异常堆栈信息。

```java
logger.error("inputParams:{} and errorMessage:{}", params, e.getMessage(), e);
```

4. 日志打印时禁止直接用 JSON 工具将对象转换成 String，可能抛出异常影响业务流程。

#### 【推荐】

1. 对 `trace`/`debug`/`info` 级别的日志输出必须进行日志级别的开关判断。
2. 生产环境禁止输出 debug 日志，info 日志有选择地输出。
3. 使用 `warn` 级别记录用户输入参数错误，不要用 `error` 级别。`error` 只记录系统逻辑出错、异常或重要的错误信息。
4. 尽量用英文描述日志错误信息。

## 三、单元测试

#### 【强制】

1. 遵守 **AIR** 原则：
   - **A**utomatic（自动化）：全自动执行，禁止用 `System.out` 人肉验证，必须用 `assert` 验证
   - **I**ndependent（独立性）：测试用例之间禁止互相调用，不能依赖执行先后次序
   - **R**epeatable（可重复）：不能受到外界环境的影响
2. 必须写在 `src/test/java` 下。
3. 新增代码要及时补充单元测试并确保通过，若影响了原有测试要及时修正。

#### 【推荐】

1. 测试粒度足够小，一般至方法级别。
2. 对不可测的代码要做必要的重构，使代码变得可测。

## 四、安全规约

#### 【强制】

1. 隶属于用户个人的页面或功能必须进行权限控制校验。
2. 用户敏感数据禁止直接展示，必须脱敏处理。
3. 用户输入的 SQL 参数必须使用参数绑定（`#`），禁止字符串拼接 SQL。
4. 用户请求传入的任何参数必须做有效性验证。
5. 在使用平台资源（短信、邮件、支付等）时必须实现防重放机制。

## 五、MySQL 数据库

### 5.1 ORM 映射

#### 【强制】

1. 禁止用 `*` 作为查询的字段列表。
2. POJO 类的布尔属性不能加 `is` 前缀，而数据库字段必须加 `is_` 前缀，在 `resultMap` 中做映射。
3. 使用 `#{}` 代替 `${}`，防止 SQL 注入。
4. 禁止用 `HashMap` 与 `Hashtable` 作为查询结果集的输出。
5. 更新数据表记录时，必须同时更新 `update_time` 字段。
6. 不要写大而全的数据更新接口，只更新需要变更的字段。
7. `@Transactional` 事务不要滥用，需要考虑各方面的回滚方案。

#### 【推荐】

1. 即使所有类属性名与数据库字段一一对应，也需要定义 `resultMap`，使字段与 DO 类解耦。

## 六、工程结构

#### 【推荐】

1. JVM 环境参数设置 `-XX:+HeapDumpOnOutOfMemoryError`。
2. JVM 的 `Xms` 和 `Xmx` 设置一样大小的内存容量。

## 七、设计规约

#### 【强制】

1. 类在设计与实现时要符合**单一职责原则**。
2. 谨慎使用继承的方式来进行扩展，优先使用聚合/组合的方式来实现。若使用继承，则要符合**里氏替换原则**。
3. 系统设计阶段，根据**依赖倒置原则**，尽量依赖抽象类与接口。
4. 注意**开闭原则**：对扩展开放，对修改闭合。同一业务域内的需求变化要通过模块或类的扩展来实现。
5. 共性业务或公共行为要抽取，使得在系统中不出现重复代码（**DRY 原则**）。
6. 可扩展性的本质是找到系统的变化点并隔离变化点。
